# BioFlow e2e test definitions

Tests in this directory are discovered by the harness loader
(`e2e/backend/loader.py`). Linear tests are `.yaml`; a Python escape hatch is
a `.py` file that uses `@test(...)` from `e2e.backend.primitives`.

## Step reference model

Steps run in order; each step's result is stored in the run state under its
`as:` alias (or a default key — `project`, `upload`, or the tool name).
References `$.a.b.c` resolve against that state. `create_project` also sets
`$.project_id`. `{{run_id}}` in a string arg is replaced with the run id.

Verbs: `create_project`, `upload`, `mcp`, `wait`, `assert`, `launch`, `find`,
`patch`, `get_object`.

- **`launch`** starts a pipeline over HTTP. Two forms: `kind: <card kind>`
  takes the body from a prior `suggest_next` result (preferred -- it tracks
  the body BioFlow builds server-side), and `endpoint:`/`body:` writes one
  out for the pipelines that have no card (QC, bamstats). An unavailable
  card fails the step with the card's own `reason`.
- **`find`** selects one item from a list by field (`in:`, `where:`), since
  `get_job` does not return a job's `result` -- pipeline outputs are reached
  through `list_objects`. Ambiguous matches fail unless `allow_many: true`.
- **`patch`** PATCHes an object; the reads path uses it to mark the uploaded
  FASTA `role: reference`.
- **`get_object`** reads an object over REST rather than through the MCP
  tool of the same name, because only REST returns `facts`. `await_fact:`
  polls until a named fact appears.
- **`wait`** defaults to polling a job's `state` to a terminal one, and takes
  `field:`/`until:` for anything else -- `field: status, until: ready` is how
  a freshly uploaded object is awaited.
- **`assert`** supports `equals`, `contains_format`, and `at_least` (numeric).

## Discovered BioFlow facts (verified against source, not recalled)

- **MCP endpoint:** `POST /api/v1/mcp` (Streamable HTTP, JSON-RPC), profile via
  `?profile=<id>`.
- **Pipeline handler kinds** (`run_pipeline` validates against
  `queue/registry.all_handlers()`): `run_qc`, `trim_reads`, `align_reads`,
  `build_index`, `call_variants`, `run_bam_stats`, `run_vcf_stats`,
  `download_assembly`, and ~45 others.
- **Job terminal states:** `succeeded`, `failed`, `cancelled`, `dead`.
- **Launch flow (important):** the intended agent path is `suggest_next` →
  each card's `launch` is `{"endpoint", "body"}` — a *complete* HTTP request
  body built server-side — posted to the REST API, *not* a `run_pipeline`
  `params` dict. `run_pipeline(kind, params)` passes `params` straight through
  as the raw handler payload, so hand-building it requires the exact
  `object_id`/`project_id`/`name`/`platform`/… shape the launch endpoints
  assemble. This is what the `launch` step does; endpoints are
  router-relative (`/pipelines/align`) and joined onto `/api/v1`.
- **Not everything has a card.** QC and bamstats are launched from their own
  tabs, not the Actions grid, so `suggest_next` returns no card for them;
  they use `launch`'s explicit `endpoint`/`body` form.
- **Card kinds** are `preprocess` (trim), `align`, `variants`, `assemble`,
  `annotate`, `quantify`, … — note trimming is `preprocess`, not `trim`, and
  there is no `qc` kind.
- **Async gaps that need waiting on**, each of which produced a real failure
  while writing the reads path:
  - An upload returns before ingest finishes; the object is `ingesting` and
    a launch against it is rejected with "is not ready".
  - An uploaded FASTA has **no role**. The align card counts only objects
    whose role is `REFERENCE`, so a reference must be PATCHed to that role
    or the card stays UNAVAILABLE ("Upload a reference to align.").
  - The align card needs the read chemistry **QC** infers, so QC must
    complete before the align card becomes available.
  - Flagstat facts (`mapped_pct`) are written by the `index_bam` job the
    align flow queues afterwards, so they appear some time *after* the align
    job reports success.
- **`facts` vs `metadata`:** measured numbers land in `facts`; the MCP
  `get_object` tool returns only `metadata`. Assertions about what a run
  measured have to read the object over REST.
- **Upload endpoint:** `POST /api/v1/projects/{id}/objects/upload` — raw bytes
  in the body, filename in `X-Filename` (percent-encoded), profile in
  `X-BioFlow-Profile`.
