# Agent notes: why the rules in CLAUDE.md are what they are

[CLAUDE.md](../CLAUDE.md) states the rules. This file records the incidents
behind them -- what broke, when, and what it cost -- for when a rule looks
arbitrary and you are deciding whether to follow it, change it, or work
around it.

Read the rule first. Come here when you want the evidence.

## Merging your own PR

**The rule:** open *and* merge your own PR once every check reports `pass`.

Reverted the 2026-08-09 rule that made merging the user's step, on
2026-08-17. Nothing ships at a merge to `main`: it is a dev trunk, and
alpha, beta and production are all downstream. A green PR sitting open is
not being reviewed, it is waiting -- and the cost is real, since `main`
moves underneath it and the next task starts from a base that excludes it.

**Why the polling is load-bearing.** `gh pr create` returns before any check
has run, so a "pending" read seconds after creation is the run not having
started, not a signal to stop watching. On #217/#314 the local suite was
green but CI's `ruff check` failed on an import-order rule (`I001`) the
local run never invoked; the fix was a one-line import split. Since you now
merge your own work, that poll is the only thing between a bad change and
`main`.

**Why `--rebase`, never `--squash`.** `main`'s history is one commit per
unit of work, first-parent (`git log origin/main --first-parent` shows the
individual subjects). `CHANGELOG.md` is generated by git-cliff from commit
subjects *and bodies*; a squash concatenates the bodies into one blob under
a single subject, which is exactly the input that generator cannot use. The
separable-commits rule also assumes the commits survive -- splitting a
mechanical rename from a behaviour change is pointless if the merge glues
them back together.

Until 2026-08-19, `AGENTS.md` told agents to use `--squash` while CLAUDE.md
required `--rebase`, so the merge strategy depended on which file a harness
loaded. `AGENTS.md` is now a symlink (#694).

**Why rebase before opening the PR, not after.** A PR opened against a stale
base either merges something it was never tested against, or sits reporting
`mergeStateStatus: DIRTY` until someone notices. Rebasing first means it is
mergeable the moment it exists.

**Why re-check the diff after resolving conflicts.** A rebase or merge can
resolve a conflict by silently dropping a hunk when a resolution is accepted
too quickly. `git diff origin/main...HEAD --stat` before pushing catches it;
"the command ran without error" does not.

## Conventional Commits and the changelog

**The rule:** `<type>(<scope>): <subject>`, imperative, lowercase after the
colon, no trailing period, ~65 chars.

Roughly 98% of the last 300 commits already followed this before it was
written down. It became load-bearing rather than tidy when the changelog
started being generated from it: a user-visible change committed as `chore`
simply disappears from the release notes, and nothing errors. A breaking
change needs `!` or a `BREAKING CHANGE:` trailer -- that marker cannot be
recovered from the diff later.

**Why the subject matters more than it looks.** It is the one line that
survives into the notes, and by then the code is not in front of the reader.
Real subjects from this repo that get it right share a shape: they name the
new behaviour and contrast it with the old one.

```
fix(frontend): record a project visit once per navigation, not per refetch
fix(queue): advance workflow nodes on every terminal path, not just complete()
feat(activity): say what each run is doing, not just what it acted on
fix(frontend): hide RECENT block entirely when zero chips fit
feat(ui): quality badge as a serif figure instead of a color dot
```

| Avoid | Why |
|---|---|
| `fix: bug fix` / `fix(ui): fix issue` | Says nothing the type didn't. |
| `feat: update ProjectExplorer.tsx` | Names a file, not a change. |
| `fix: address PR feedback` | Meaningless outside the PR. |
| `chore: various improvements` | Bundles unrelated work *and* hides it. |
| `feat: WIP` | Admits it isn't a unit of work. |

If you cannot write a clear subject, the commit is usually telling you it
does two things.

## Ruff runs locally, not in CI

The "Lint with ruff" step was removed from `build-check.yml` on 2026-08-19:
it failed PRs on line length, import order and ambiguous variable names --
trivia that blocks a merge without telling anyone anything -- and for a
single-user local tool that trade is not worth it.

**It is kept at commit time because it is not only a style checker.** The
same run that reports `E501` reports `F821` (a name used but never
imported) and outright syntax errors. Both showed up for real on
[#691](https://github.com/syntheticgio/bioflow/pull/691): an unclosed
`ToolMeta(` made `tools.py` a syntax error, and `suggestion_service.py`
used `SidecarRole` without importing it, which would have raised
`NameError` the first time an SNF sidecar reached the card builder.

**Why `--config` is explicit.** `backend/pyproject.toml` only auto-applies
under `backend/`, so `ops/` and `e2e/` would otherwise fall back to ruff's
smaller built-in rule set
([#466](https://github.com/syntheticgio/bioflow/issues/466)). Config
resolution also depends on the invocation directory, so a run from
`backend/` and CI's run from the repo root disagree
([#510](https://github.com/syntheticgio/bioflow/issues/510)).

**Why the hook lints the whole tree.** A staged-files-only check reports
green while a later commit breaks a file it didn't touch.

**Why `core.hooksPath` behaves oddly in worktrees.** The value lives in the
shared `.git/config` and a relative path resolves against the *main*
worktree, so a hook run from a worktree is the main checkout's script. Both
hooks re-derive the tree with `git rev-parse --show-toplevel`, so a worktree
lints its own code. Don't "fix" this by pointing `hooksPath` at a worktree
copy; that breaks the main checkout.

## Fixing errors you did not cause

**The rule:** fix every error a run reports, not only yours.

Triaging by authorship is wrong here because this is a single-user repo --
"someone else will fix it" resolves to nobody, and a pre-existing error that
survives your PR has now survived a second person looking straight at it.

On 2026-08-19 a full-tree ruff run during #693 reported 17 errors across
`backend/app`, `backend/tests`, `ops` and `e2e`, only a handful from that
branch's work. One of the "pre-existing" ones was `F821 Undefined name
'SidecarRole'` in `suggestion_service.py` -- a live `NameError` on every
Actions-tab evaluation of the SV-merge card, shipped and unnoticed.
Triaging by authorship would have left a real bug in place under a green PR.

**`--fix` is a starting point.** Removing an "unused" import can be correct
or can be the symptom of a missing usage, and it will happily leave a quote
style the file does not use. Run the tests for every file it touched.

## One running instance, not dev/prod

**The rule:** `docker compose up` on port 5173 is the only way this app
runs. Don't build a dev/prod split.

Compose auto-loads `docker-compose.override.yml`, and that override is not
optional or occasional -- it *is* how this app runs. It gives hot-reload on
both sides (bind-mounted source, `uvicorn --reload`, `vite dev`).
`docker-compose.yml`'s own `web` service target (`prod`, static nginx) is
not what is deployed day to day.

Since [#37](https://github.com/syntheticgio/bioflow/issues/37) the base file
names registry tags at `ghcr.io/syntheticgio/bioflow-*`, and the `build:`
directives live in the override. **Anything that bypasses the override runs
the last published build, not the working tree** -- it starts cleanly and
serves stale code with nothing in the output saying so. That is why
`--build` is what ties the running stack to the checkout, and why a rebuild
that "seems not to take" is usually a missing flag rather than a code
problem.

**Why `worker` needs an explicit restart.** `api` runs `uvicorn --reload`
and `web` runs `vite dev`, so their bind-mounted source takes effect on the
next request. `worker` bind-mounts `./backend/app` too but runs `python -m
app.worker_main` with no reload mechanism, so it keeps executing whatever
was loaded at process start. A pipeline job then appears to run with the fix
while silently executing the old in-memory code -- which reads as "the fix
didn't work" when it simply was never picked up.

## Worktrees and the compose project name

**The rule:** plain `docker compose` targets the one main-checkout stack;
a worktree's code goes through `./ops/worktree-up.sh`.

The bind mounts in the override are relative (`./backend/app`,
`./frontend/src`), so Compose resolves them against the invocation
directory -- while the project name is pinned to `biopipe`. Running `docker
compose up` inside a worktree therefore does not create a second stack: it
silently recreates *the* stack with its source pointing at that worktree,
with no error and no warning. Port 5173 then serves that branch, a merged
change appears to be missing from the running app, and the handler simply
never shows up in the worker's `handlers_loaded` line.

A `PreToolUse` hook (`ops/hooks/block-compose-in-worktree.sh`) blocks bare
`docker compose` from a worktree for exactly this reason. It tokenizes the
command (`ops/hooks/compose_target.py`) rather than matching the phrase, so
writing *about* compose is not blocked -- a heredoc, a `gh issue create`
body, or a `grep` all pass, as does a compose call addressed to a container.
Before [#549](https://github.com/syntheticgio/bioflow/issues/549) it matched
the substring anywhere and blocked all four.

**Two things `worktree-up.sh` does that are easy to get wrong by hand.** It
passes `--env-file <main checkout>/.env`, because `.env` is gitignored and a
worktree has none -- without it `BIOINFO_HOME` falls back to the compose
default and Docker silently creates that path as an empty directory. And on
first launch it copies the main stack's database in with `mongodump |
mongorestore`, since a new project name means an empty database. That copy
is a snapshot, not a mirror; `--reseed` refreshes it. `/data` *is* shared
deliberately -- fine for a UI or read-path check, worth a thought before
running a pipeline that rewrites an existing artifact.

**Why leftover stacks matter.** On 2026-08-12 a full-suite run hung twice at
~10% with mass errors, on code that was fine; four *other* worktree stacks
were still up from earlier tasks, three with live Mongos and one with
workers in a restart loop. Since `conftest.py` dropped every collection in
`biopipe_test` at session start, each run was wiping the others' data
mid-test. That reads as flakiness -- a rotating handful of DB-touching tests
failing, different ones each run, all passing in isolation -- and it costs
an afternoon to trace back to a container nobody remembered starting.
Per-run database names (#693) have since removed that specific collision,
but a stack you started is still yours to bring down.

**Why `--prune` only removes orphans.** A stack whose worktree still exists
is somebody's live test run. `git worktree list` is the authority; a
detached-HEAD worktree is matched by directory name, because that is the
slug `worktree-up.sh` itself falls back to.

## Test isolation and parallelism

**The rule:** `make test` runs in parallel; every worker gets its own
database.

Before [#693](https://github.com/syntheticgio/bioflow/pull/693),
`conftest.py` hardcoded the database name `biopipe_test`, so two runs
sharing one Mongo wiped each other mid-test. Measured on one unchanged tree
while the stack's own `api` container was also running tests: 7 failed, then
1872 passed, then 5 failed. With a private replica set: five consecutive
runs at identical counts.

Databases are now named `biopipe_test_{run_token}_{worker_id}` -- the token
separates concurrent *sessions*, the worker id separates workers within one.
Two full suites have been run simultaneously against a single Mongo, both
green at their sequential counts. The worktree script's private Mongo is
therefore belt-and-braces now rather than load-bearing.

**Why 12 workers and not `auto`.** The Docker VM reports 24 CPUs against
12.4 GB of RAM, so `auto` sizes the run by the resource that is not scarce.
Measured on the full suite post #756 (probe cost removed): 8 workers ~45s
parallel, peak ~0.76 GB; 12 workers ~36s parallel, peak ~0.48 GB. 12 is now
meaningfully faster than 8, and concurrent runs stay under ~1 GB peak,
leaving headroom for a second agent on the 12.4 GB VM. Peak memory at 12
workers was ~0.48 GB, concurrent two runs ~0.94 GB.

In CI the same reasoning gives a different number: inside a container
`os.cpu_count()` reports the *host's* cores and ignores the cgroup quota, so
`-n auto` oversubscribes badly. The workflow reads the quota from
`/sys/fs/cgroup/cpu.max` instead.

**Why the run-token sweep skips unmarked databases.** An unstamped database
is one being *born*, not one abandoned: a concurrent run creates it and only
then writes its marker. Sweeping on a missing marker turns that gap into a
race the other run loses -- measured as `init_beanie` dying with
"OperationFailure: Operation not permitted" when its index build landed on a
database the sweep had just dropped.

**Why cleanup is keyed on this run's failures, not exit status.** Gating on
`exitstatus == 0` meant a suite carrying any long-standing red test never
cleaned up at all: 51 databases had accumulated across a dozen runs.

**Why `docker compose exec api pytest` is main-checkout-only.** The `api`
container bind-mounts the *main* repo's `backend/app` and `backend/tests`,
so running it from a worktree silently tests main's code. Every result
describes the wrong tree with no error saying so.

**Why `pytest` and never `python -m pytest`.** The image puts a tool venv
(`/opt/medaka/env/bin`) ahead of the app interpreter on `PATH`, so both
`python` and `python3` resolve to an environment with none of the app's
dependencies -- "No module named pytest", from an image where pytest is
demonstrably installed.

**Why a real database beats another fixture sometimes.** The Actions tab's
suggestion rules passed a full green suite while getting two things wrong
that one look at a real project exposed: `protein.faa` and
`cds_from_genomic.fna` counted as alignable references because they are
FASTA, and the same assembly stored twice counted as two. Both made a
project with one usable reference refuse to align. The tests were green
because they fed the rules hand-built objects that already looked the way
the rules expected.

**Why the worktree script leaked two volumes per run ([#719](https://github.com/syntheticgio/bioflow/issues/719)).**
`run-worktree-tests.sh`'s private Mongo (and, with `--with-sshd`, the sshd
sidecar) both declare anonymous `VOLUME`s in their images -- `mongo:7`
declares `/data/db` and `/data/configdb`; `lscr.io/linuxserver/openssh-server`
declares `/config` (confirmed via `docker history --no-trunc`). Neither
`docker run -d --rm` nor the cleanup trap's `docker rm -f` removes an
anonymous volume -- only `-v` does. The trap fired every time and really did
remove the container, so `cleanup()` *read* as correct; it just silently left
one or two ~340 MB volumes behind per run. 237 runs was 75 GB of dangling
volumes before anyone noticed, because nothing in the repo runs
`docker system df` or reports volume count. Fixed by changing `cleanup()` to
`docker rm -fv`, guarded against regressing by
`ops/tests/test_worktree_test_volume_leak.py`, which starts a real
`mongo:7`/sshd container, cleans it up the same way, and asserts the dangling
volume count is unchanged -- plus a static check that `cleanup()` still
passes `-v`.

That 75 GB (plus reclaimable build cache and images) does not remove itself,
and nothing here should: `docker volume prune` is machine-wide and does not
know which volumes belong to this project versus another one running
alongside it. Reclaim manually, dry-run first:

```bash
docker volume ls -qf dangling=true | wc -l   # how many, before touching anything
docker volume prune                          # asks for confirmation; removes all dangling volumes
docker builder prune --dry-run               # reclaimable build cache, without deleting
docker builder prune                         # actually reclaim it
docker image prune -a --dry-run              # unused images, without deleting -- this repo
                                              # rebuilds the backend image often, so check what
                                              # would go before running for real
```

## Closing out a TODO entry

**The rule:** when work lands, mark the entry ` — FIXED`, note what shipped,
and move the whole entry to `docs/TODO-done.md`.

On 2026-07-31 an audit found three of seven entries described work that had
shipped days earlier -- all three fixed by one plan that ran to completion
without anyone touching the backlog. The cost is not tidiness: one stale
entry advised deleting `JobContext.extend_lease` as dead code, and by then
four handlers were calling it. Acting on the TODO would have broken working
code.

**Say what the implementation did differently.** Every entry closed so far
departed from its own plan somewhere, and that delta is the most valuable
sentence in the entry. Record measurements if the entry claimed a number:
"6-15s" becoming "0.025s" is what makes the fix checkable later.

**Delete an entry only when it was wrong to begin with**, not merely done. A
`— FIXED` entry is a record; a deleted one is a question someone will ask
again.

**Don't trust a plan's checkboxes.** Nothing ticks them. Both surviving
plans in `docs/superpowers/plans/` show zero of their 66 and 49 boxes
checked while their code is demonstrably merged. `grep` for the symbol the
entry names.

## Hand-maintained registries keyed by an enum

**The rule:** before adding a case to a dict keyed by an enum, work out
which of three kinds it is.

Adding STAR found this shape in `results._SIDECAR_ROLES` and cost a
`build_index` job that reported success while storing none of its eight
index files. The full suite stayed green throughout, because every fixture
fed the appliers roles already in the allowlist.

[The registry audit](superpowers/specs/2026-08-05-registry-audit-design.md)
walked every registry named in
[#11](https://github.com/syntheticgio/bioflow/issues/11) and found the shape
splits three ways -- only one of which should be "fixed" by forcing
coverage:

- **Genuinely derivable.** `results._SIDECAR_ROLES`, and `schemas.ROLE_FIELDS`
  / `FORMAT_FIELDS` (which hold real per-role data, so full derivation is
  wrong, but each has a companion `frozenset` covering every member the main
  dict omits, with a comment on each saying why). `set(TheEnum) ==
  set(main_dict) | companion_set` is the test both carry. **Copy this one.**
- **Intentionally partial, where forcing coverage is the bug.**
  `enrich._TOKEN_SEQUENCE_TYPES` maps an open vocabulary of filename tokens
  to `SequenceType`; `detect_sequence_type`'s contract is to return `None`
  when a filename doesn't say. Forcing every member to be reachable would
  turn "the name doesn't say" into a wrong guess -- worse than the STAR
  failure, not a fix for it. These need a written inclusion rule and a
  *reachability* test in the other direction.
- **Keys owned outside this repo.** `ncbi_assembly_components.COMPONENTS` is
  keyed by NCBI's `--include` names; a bad key fails loudly at the command
  line, so there is no silent-skip risk on the key side. The risk was
  internal: `COMPONENT_ORDER`, a hand-written parallel tuple, had zero tests
  tying it to the dict -- a component in one and not the other would be
  invisible in the download dialog with no error anywhere. Fixed with
  `set(COMPONENT_ORDER) == set(COMPONENTS)`.

**Run partition pairs together.** `node_types.py`'s
`NODE_TYPES`/`EXCLUDED_LAUNCHES` split is a partition: every launcher must
be classified *and* not classified as both. #355 fixed the first test for
`launch_annotation_stats` with two independent commits -- one added a
`NodeTypeSpec`, the other added the exclusion -- and both landed, satisfying
the test the issue named while silently failing the second one in the same
class. It stayed red until someone ran the whole file
([#366](https://github.com/syntheticgio/bioflow/pull/366)).

## Adding a pipeline tool

**The rule:** registering in `tools.py` is only half the change.

`suggestion_service.py` decides which tool each Actions-tab card recommends
and is hand-maintained, so a new tool no rule can pick will never be
suggested however cleanly it installs. The failure is silent: installing
Flye does not make the Assemble card light up -- it leaves a card reading
"No assembler is installed" next to an installed assembler.

The Software help page renders `TOOL_META` directly, and
`test_every_tool_is_documented` requires `homepage`, `citation`, `license`
and `usage`. A new tool fails that test until they are filled in, which is
the point: the alternative is a reference page that silently omits it.

**Verify license and citation against the project's own repository rather
than recalling them.** A wrong license claim on a page that reads as
authoritative is worse than a blank field -- which is why `repository` and
`citation_url` are deliberately *not* required.

**Write `usage` as behaviour, not flags.** Flags change whenever a runner is
tuned, and nothing can mechanically catch a stale `usage` string. The
comment on `ToolMeta.runnable` spent a long time citing cutadapt and
Trimmomatic as tools nothing dispatches to, years after `trim_reads` grew
its three-way dispatch. Nothing failed, because a comment cannot.

**Two traps when testing availability**, both of which produced tests that
silently read the host while appearing to control it:

- `aligner_registry`'s specs are frozen dataclasses that captured
  `tools.minimap2` as a function object at import time, so patching
  `app.pipelines.tools.minimap2` never reaches `spec.tool`. Patch `spec_for`.
- The image ships most tools installed, so a test asserting a card is
  *available* passes whether or not its patch worked. Assert the card flips
  to unavailable when the probe is patched off -- that is the direction that
  fails when the seam breaks. The same shape bit `test_offered_for_fastq`
  (kraken2) and `test_merge_structural_variants_succeeds_on_same_reference`
  (sniffles), which were green in the backend image and red on a CI runner.

## AI features

**The rule:** go through `app/services/ai/`, and a new feature needs a new
`TaskSlot`.

The settings page renders one row per enum member, so the enum is what makes
a feature routable. A call site that reuses `FILE_SUMMARY` because it is
already there silently ties two unrelated features to one provider, with no
way for the user to separate them.

**`complete()` never raises and never returns None.** It returns
`Completion` or `Failure`. Checking `if result is None` -- the shape the old
`llm_client` had -- passes type-checking, reads as correct, and treats every
failure as a success.

**Thread handlers must not call `asyncio.run()`.** `HandlerMode.THREAD`
handlers run in a worker-pool thread with no event loop, and `asyncio.run()`
looks like the obvious way to get one -- but this process's Mongo client is
a module-level `AsyncIOMotorClient` bound to the loop `connect_to_mongo()`
ran on, and a second loop makes Motor raise "attached to a different loop"
the instant a query touches it. That is exactly what broke `summarize_object`
the first time it ran against a real configured provider, with every unit
test green, because every test mocks the seam that made the call. Use
`app.db.client.run_from_thread`; `summary_handlers._resolve_sync()` is the
worked example. Thread handlers also get no automatic failure recording (that
write needs the loop too) -- use `complete_sync()` and return the reason in
the handler's own payload.

Failures are recorded on the provider document, which the settings badge
reads. A provider can therefore go red from a real job rather than only from
"Fetch models" -- deliberate, and the reason an expired key is visible
rather than silently stopping summaries.

## Querying computation records

**The rule:** never query `job_timings` directly to fit or summarize
anything; go through `timing_service._modelled()` or `records_for_object()`.

Failed runs are in that collection too, and the consumers differ on whether
they want them: provenance and OOM detection need failures, the predictive
models must never see them. Recorded in
[the computation-records design](superpowers/specs/2026-08-03-computation-records-design.md).
Before it, the collection held successes only, so no query needed an outcome
filter and none had one -- the invariant now lives in the read paths
instead, which is the part that is easy to get wrong.

The failure mode is silent and points the wrong way. A job that OOM-killed
at ninety seconds looks like a fast, cheap run, and its peak RSS is the
ceiling it *hit* rather than what it needed. A few of those drag estimates
downward -- predicting jobs are cheaper than they are, which is exactly the
direction that causes the next OOM. Nothing raises; the numbers are quietly
low.

Resource fields are null for runs under 60 seconds, so anything fitting
against them works with a subset of rows. A null peak is a short job, not a
failed sampling.
